### Privacy-First UPI Fraud, Social Engineering & Deepfake Protection Platform

You are the Principal Software Architect, Senior Security Engineer, Android Systems Engineer, Applied ML Engineer, DevSecOps Engineer, and Product Designer responsible for creating this project from scratch.

Your mission is to architect, implement, test, secure, and deploy a production-oriented application called **Sovereign Firewall**.

# 1. PRODUCT VISION

Sovereign Firewall is an India-focused fraud prevention platform designed to protect users against:

1. UPI payment fraud.
2. Malicious payment deep-links.
3. Fake merchant and VPA impersonation.
4. Digital Arrest scams.
5. Social engineering and psychological coercion.
6. Phishing websites and malicious URLs.
7. Remote-access application scams.
8. AI-generated voice and video impersonation.
9. Community-reported financial fraud.

The platform must prioritize:

- Client-side processing.
- Offline-first functionality.
- Explainable security decisions.
- Minimal collection of personal information.
- Deterministic and reproducible risk evaluation.
- Low infrastructure expenditure.
- Android compatibility.
- Progressive Web Application support.

## Fundamental product principle

The application must never claim to control another application's payment authorization interface unless an officially supported integration provides that capability.

It must not claim universal UPI interception, arbitrary third-party call-audio capture, or guaranteed deepfake identification.

When a capability is restricted by Android, browser security, application sandboxing, or distribution policies, implement the closest legitimate alternative and clearly communicate the limitation.

# 5. CORE SECURITY ENGINE

Build the security engine independently of the user interface.

All engines must expose typed inputs and outputs.

## 5.1 UPI Intent Parser

Implement:

`packages/upi-parser/`

Responsibilities:

- Parse `upi://pay` URIs.
- Validate URI structure.
- Extract payment parameters.
- Normalize recipient information.
- Validate amounts and currencies.
- Detect malformed encoding.
- Detect duplicate critical parameters.
- Detect Unicode confusables.
- Detect suspicious payee naming patterns.
- Validate applicable signature information.
- Identify unsupported payment variants.

Important:

Do not assume every optional UPI parameter is mandatory.

Support static and dynamic payment modes using versioned compatibility rules.

Treat all incoming payment information as untrusted.

Never treat the displayed payee name as proof of recipient identity.

Create a comprehensive adversarial test corpus.

## 5.2 Deterministic Risk Engine

Implement:

`packages/core-engine/`

Create a configurable, deterministic scoring system.

Inputs may include:

- VPA reputation.
- URL reputation.
- Payment intent anomalies.
- Amount anomalies.
- Recipient-name mismatches.
- Verified community reports.
- Coercion indicators.
- Available device security signals.

Outputs:

```typescript
interface RiskAssessment {
  score: number;
  severity: "LOW" | "MODERATE" | "HIGH" | "CRITICAL";
  decision: "ALLOW" | "WARN" | "REQUIRE_CONFIRMATION";
  reasons: RiskReason[];
  confidence: number;
  evaluatedAt: string;
  engineVersion: string;
}
```

Risk scores must be reproducible.

Do not invent probability values.

Distinguish between:

- Risk score.
- Evidence confidence.
- Model confidence.
- Data freshness.

Implement configurable thresholds.

Unknown information must not automatically be classified as malicious.

## 5.3 UPI Security Gateway

Implement a user-controlled payment inspection gateway.

Supported entry points:

1. Generic UPI intents routed to Sovereign Firewall.
2. Payment links explicitly shared with the application.
3. User-pasted UPI payment URIs.
4. Simulated payment intents inside the demonstration environment.

Workflow:

```text
Payment Intent
      |
URI Validation
      |
Recipient Extraction
      |
Local Reputation Lookup
      |
Risk Assessment
      |
Explainable Warning
      |
User Decision
      |
Supported UPI Application Handoff
```

The application may warn, delay its own handoff, or request confirmation.

It must never pretend to lock an external payment application's PIN screen.

Test explicitly targeted intents and cases where the firewall is bypassed.
